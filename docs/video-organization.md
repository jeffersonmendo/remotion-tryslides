# Video and composition organization

## One Remotion project, multiple videos

Keep TrySlides videos in this project rather than creating a separate Remotion installation for every video. Each production has its own resource package, implementation, render media, and registered delivery composition. Share visual components only where there is real reuse.

This document defines implementation organization. Product facts and audiovisual direction remain in [the shared reference](tryslides/README.md); planning, approval, and learning follow [the video workflow](tryslides/video-workflow.md).

## Directory convention

Use the same English kebab-case video slug across the three per-video directories. The following illustrates a future production, not folders or footage generated by the resource command:

```text
resources/
  getting-started/
    README.md
    brief.md
    script.md
    timeline.md
    recording-checklist.md
    assets.md
    review.md
    feedback/
    images/
    recordings/
    audio/

src/
  index.ts
  Root.tsx
  videos/
    getting-started/
      GettingStarted.tsx
      scenes/
        Opening.tsx
        CreatePresentation.tsx
        EditorOverview.tsx
        Closing.tsx
  components/
    ChapterTitle.tsx
    AnimatedText.tsx
    ScreenRecording.tsx

public/
  videos/
    getting-started/
      create-presentation.mp4
      narration.wav
```

Create source files, scene folders, and media copies only when needed for an approved production. The component names and media above are examples, not dependencies or requirements to create in advance.

## Responsibilities

- **`resources/<video-slug>/`:** the production archive: current plan, original recordings, supplied assets, feedback, decisions, and review. It is not automatically served as media.
- **`src/videos/<video-slug>/`:** the implementation belonging to one video. Its main component assembles the video; `scenes/` contains meaningful scene units. Keep video-specific helpers local instead of importing internals from another video.
- **`src/components/`:** genuinely shared presentation components such as a recurring chapter heading or a common recording frame. Do not build a large speculative library before the first video.
- **`public/videos/<video-slug>/`:** only cleared, render-ready copies required by that video. Never place scripts, feedback, private raw captures, or secrets here. Public media is potentially accessible while serving or hosting a bundle; exporting a video does not itself authorize hosting its source media.
- **`src/Root.tsx`:** the explicit registry of delivery compositions and any supporting registrations needed for Studio editing. It does not own scripts, footage processing, or scene implementation.
- **`src/index.ts`:** the Remotion entry point that registers the root. Adding another video should not require replacing this entry point.

Use `assets.md` to map source asset IDs and original paths to the actual render-ready copies. Do not maintain two competing editable masters. Shared licensed brand assets can live in `public/shared/` once they are needed; do not duplicate them under every video or assume they already exist.

## Delivery compositions and scenes

Register each complete video deliverable as its own `<Composition>` with a unique, descriptive literal ID, its main component, and appropriate duration, frame rate, width, and height. Examples of IDs are `GettingStarted-Landscape` and `LaunchCommercial-Vertical`; these are naming examples, not registered videos.

Keep registrations explicit in JSX rather than generating independently editable videos with a loop. Keep editable metadata and defaults on their registration nodes as directed by the installed composition skill. Different videos can have different formats and durations without becoming separate projects.

A scene is a part of a video's audiovisual timeline, not automatically another delivery video. Keep ordinary implementation details local. When the installed Remotion multi-scene/interactivity guidance calls for connected scene registrations to support independent Studio editing, register the same exported scene components with useful defaults. Those are supporting editor registrations, not extra finished deliverables. The one-delivery-composition convention must not disable scene editing.

Follow the installed Remotion skills for the actual timing structure, connected scenes, clips, captions, transitions, and duration accounting. Give independently editable scene or clip instances their own authored nodes rather than collapsing them into one generated source target. Do not encode a second unrelated timeline in configuration that disagrees with the authored edit.

## Variants and navigation

- A landscape and vertical cut with different framing or timing should have separate composition registrations and clear IDs. They can share useful scene components while keeping format-specific layout deliberate.
- A resolution-only export does not require copying the entire video implementation. Follow the actual output requirements and installed rendering guidance.
- Keep delivery variants and derivatives of the same source video in its source directory; they are not separate short-form productions. Record the canonical video and variants in the package index and timeline.
- Use Remotion `<Folder>` groups when they improve Studio navigation, for example a group per production with delivery variants and clearly separated supporting scenes. Do not impose a large category hierarchy before it is useful.
- Render to a distinct output path, such as `out/getting-started/landscape.mp4`, so one video or variant does not overwrite another. Record export paths in the package index. Do not overwrite an approved export merely because the renderer permits it.

## Long-form delivery families

Follow [deliverables and exports](tryslides/deliverables-and-exports.md). Every production includes one 12–20 minute source-video composition, four derived 40–60 second short/reel compositions, one YouTube-thumbnail Still, four cover Stills, and one 1080 × 1080 square-post Still. This is the required structure, not an optional long-form variant. Do not register a standalone short-only production. Keep them under the same production slug and map them in `deliverables.md`.

Organize cutdowns and static designs in local `shorts/` and `stills/` directories when needed. Share useful scene/layout implementations but register independently editable deliveries explicitly, with unique IDs. Keep supporting scene registrations separate from the deliverable count. Do not create empty source files or registrations during resource scaffolding.

## From package to implementation

1. Run `npm run create-video -- <video-slug>` to create the empty production package only.
2. Fill the plan, gather required recordings and other materials, and obtain approval according to the workflow.
3. At production time, create `src/videos/<video-slug>/` and implement the required scenes. Add only render-ready media to `public/videos/<video-slug>/` as needed.
4. Register the delivery and necessary supporting compositions explicitly in `src/Root.tsx`. Preserve existing videos and their stable IDs.
5. Record composition IDs, source entry, media mapping, preview information, and intended export paths in the resource package.
6. Verify the chosen composition and relevant existing compositions after shared changes. Run relevant checks and the installed skills' preview/review workflow. Render final output only when requested.

The resource generator deliberately does not create source files, move media, modify `Root.tsx`, open Studio, or start a render. Scaffolding is not approval to produce a video.

## Current starting point

The source structure now contains `src/videos/` for approved productions and `src/components/` for genuinely shared components, with a short guide in each directory. `src/index.ts` continues to register `RemotionRoot`.

`src/Root.tsx` intentionally returns no compositions until the first approved production is implemented. The unused generic `src/Composition.tsx` scaffold was removed rather than moved into a fake video folder. Studio has no real videos to select or render yet; the empty registry is not an error to conceal with dummy compositions.

Add per-video source directories, actual scene components, and render media when required. The resource generator remains planning-only and does not modify this source structure or the registry.

## Changing shared components

Keep a change local when its reason applies to only one video. Promote a reusable component when its purpose is shared, not merely because two scenes look vaguely similar. Check affected videos after a shared change and record meaningful outcomes in their reviews when applicable. A new production must not silently change the look or timing of an approved existing video.
